# Vision Lab 下一階段研究計畫：雙軌時序判斷

## 1. 計畫定位

- 狀態（2026-10-08）：離線工具與自錄開發候選已實作，停在 Review；未凍結規則、完成獨立驗證或接入正式 App
- 研究主題：快軌高確定性事件＋慢軌低頭情境觀察
- 核心目標：降低正常低頭閱讀被誤判為睡眠的提醒，同時保留對明顯分心、趴下與離席的反應
- 研究原則：MediaPipe 每支影片只跑一次；所有時間窗、投票與事件規則都由逐幀 CSV 後處理

最新實作進度、已有結果與未解問題請先讀
[`vision-lab-dual-track-progress.md`](vision-lab-dual-track-progress.md)。下列是研究目標與驗收設計，
不是已驗證的辨識成效；V1／V2 開發比較不替代 test6～test9 或 test10／test11。

實際開發順序、檔案地圖、命令與分段驗收請使用：
[`vision-lab-dual-track-handoff.md`](vision-lab-dual-track-handoff.md)。

本階段不再追求用單一幀或單一門檻「證明使用者睡著」。研究重點改為：系統在看到不同強度的
視覺證據時，應該多快介入、何時保持沉默，以及何時承認證據不足。

---

## 2. 研究背景

既有實驗得到以下結果：

1. 因果 3-of-5 可以減少短暫抖動，但無法修正持續性的分類偏差。
2. 個人化 EAR P90 改善部分正面睜眼誤判，但低頭、遮擋與拍攝角度仍會影響眼部可靠度。
3. 固定頭部深度、動態閉眼 arm、肩膀相對位置等規則，在不同影片間出現明顯的誤報／漏失取捨。
4. test6～test9 的低頭睡眠片段中，臉部整體可見率只有 36.4%；test9 只有 17.5%。
5. 臉可見時，低頭閱讀與低頭睡眠的融合眼部 openness 分布高度重疊，沒有可泛化的單一門檻。

因此，下一階段不再繼續微調單一 EAR、Pitch 或肩膀門檻，而改測試「依事件確定性採用不同時間尺度」
是否能得到更符合產品需求的提醒結果。

---

## 3. 研究問題與假設

### RQ1：雙軌策略能否降低正常閱讀誤提醒？

**假設 H1：**將持續低頭交給 2–3 秒慢軌觀察，而不是立即判成睡眠或趴下，可降低低頭閱讀的
誤報事件與狀態切換。

### RQ2：慢軌是否仍能保留有用的疲勞訊號？

**假設 H2：**整合一段時間內的閉眼證據、頭部下降與姿勢變化，可保留多數刻意演出的打瞌睡／
低頭睡眠事件，但會增加約 2–3 秒的合理偵測延遲。

### RQ3：保留不確定狀態是否比強制二分類更適合提醒？

**假設 H3：**加入 `unknown_low_head`，只在證據充分時輸出 `drowsy_like`，能減少錯誤宣稱與過度
提醒；不確定狀態可在持續過久時使用一次中性詢問，而不是直接宣稱使用者睡著。

## 4. 雙軌架構

### 4.1 快軌：高確定性事件

快軌沿用目前正式 evaluator 的輸入與既有判斷，不在本實驗重新調整特徵門檻：

| 事件 | 處理原則 | 提醒方向 |
| --- | --- | --- |
| `user_missing` | 臉與 Pose 均消失後依既有防抖確認 | 只記錄，不對空位提醒 |
| `distracted` | 明顯頭部偏移／轉頭，由既有邏輯確認 | 持續成立才提醒 |
| `posture_down` | 必須有正式姿勢幾何的強證據 | 可較快介入 |
| 正坐持續閉眼 | 眼睛可靠時沿用既有閉眼證據 | 交給既有疲勞提醒策略 |

快軌的目的不是追求單幀反應，而是避免低頭情境的 2–3 秒觀察窗拖慢本來就明確的事件。

### 4.2 慢軌：低頭情境

當低頭候選持續成立，但尚未具有明顯趴下證據時，進入慢軌：

```text
持續低頭候選
    ↓
蒐集最近 2 秒或 3 秒證據
    ├─ 有閉眼＋頭部下降／點頭等交叉證據 → drowsy_like
    ├─ 姿勢穩定，未出現足夠疲勞證據      → reading_like
    └─ 臉部遮擋、品質不足或證據互相衝突  → unknown_low_head
```

慢軌只使用現有 CSV 能重現的資料：

- 低頭候選持續時間
- 臉部與 Pose 可見率
- 眼睛可靠率與閉眼證據累積時間
- Pitch 的範圍、趨勢與快速下降／回升
- 鼻子相對個人 baseline 的深度變化
- 鼻子、肩膀位置與 visibility
- 頭部是否回正，以及回正後穩定時間

`reading_like` 只代表「目前沒有足夠理由提醒」，不是證明使用者一定在閱讀；
`drowsy_like` 代表「有足夠疲勞風險證據可介入」，不是醫學上的睡眠判定。

### 4.3 慢軌候選判斷原則

為避免再形成一條容易過度擬合的總分，本輪先採可解釋的交叉證據：

- 單獨低頭深度達標：不足以判 `drowsy_like`。
- 單獨看不到臉或眼睛：不足以判 `drowsy_like`。
- 單獨 EAR／eye openness 偏低：不足以判 `drowsy_like`。
- 至少需要兩類不同來源的時序證據，例如：
  - 可靠閉眼持續一段時間＋接著頭部下降；或
  - 頭部明顯快速下墜／回彈＋姿勢持續低下；或
  - 正式姿勢幾何明顯趴低＋一段時間沒有恢復。
- 資料品質不足或證據矛盾時，輸出 `unknown_low_head`，不得用缺值當作閉眼證據。

### 4.4 狀態優先序

當兩條軌道同時有輸出時，暫定優先序為：

```text
user_missing
→ 明顯 posture_down
→ 明顯 distracted
→ 慢軌 drowsy_like
→ 慢軌 unknown_low_head / reading_like
→ normal
```

此優先序必須寫入測試，避免同一幀因實作順序不同而產生不同結果。

## 5. 實驗設計

### 階段 A：離線規格與工具

1. 保留原始 `frame_features.csv`，不得覆寫。
2. 新增獨立後處理器，從相同 CSV 產生雙軌逐幀結果與事件 CSV。
3. 每幀至少記錄：
   - `fast_state`
   - `low_head_candidate`
   - `slow_state`
   - `slow_window_ms`
   - `evidence_eye`
   - `evidence_motion`
   - `evidence_posture`
   - `data_quality`
   - `final_state`
4. 同一輸入與參數重跑兩次，輸出必須逐位元相同。
5. 快軌結果需與凍結的正式 evaluator 回放一致，避免慢軌意外改變分心、趴下或離席。

### 階段 B：既有資料開發比較

使用 test6～test9 作為**開發／回歸資料**，不可再稱為獨立驗證。

只比較以下三組，不進行大量參數掃描：

| 策略 | 說明 |
| --- | --- |
| 現行基準 | 目前凍結的正式 evaluator／提醒策略 |
| 雙軌 2 秒 | 慢軌觀察最近 2 秒 |
| 雙軌 3 秒 | 慢軌觀察最近 3 秒 |

選擇 2 秒或 3 秒時，以閱讀誤報、睡眠事件命中與延遲的整體取捨決定；不得只挑單支影片最好看的結果。

### 階段 C：凍結規則

完成既有資料比較後，必須先寫下並 commit：

- 慢軌視窗長度
- 各類證據成立條件
- 狀態優先序
- 事件開始與解除條件
- 缺值／低品質資料的處理方式
- 提醒策略與冷卻方式

規則凍結後，才可觀看新的驗證影片結果。

### 階段 D：新影片獨立驗證

至少錄製兩支未參與調參的影片，每支約 90 秒；若檔案過大可降低解析度，不縮短關鍵片段。

#### test10：混合工作切換

- 正常看螢幕
- 低頭讀書
- 讀書與查電腦資料來回切換
- 短暫眨眼／閉眼後繼續閱讀
- 一次明顯分心或轉頭
- 一次離席再回來
- 不安排真正睡眠，主要測負樣本與快軌回歸

#### test11：低頭疲勞情境

- 正常看螢幕
- 低頭閱讀
- 一次「先閉眼、接著點頭下降」的打瞌睡
- 一次維持低頭不動的睡眠姿勢
- 一次明顯趴下
- 回正後正常工作

Ground Truth 以連續時間區段標記，不需逐幀人工標註。轉場可保留 `transition` 或在計算主要
Precision／Recall 時另外報告，不得悄悄刪除難判斷片段。

### 階段 E：正式 App 小規模試用

只有離線驗證通過後，才將凍結策略放入正式 App 的 feature flag；預設仍關閉。

請至少一位未參與規則開發的人自然讀書／工作 45–60 分鐘，記錄：

- 總詢問次數
- 有用提醒次數
- 不需要／誤報次數
- 當時活動
- 使用者選擇「繼續專注／休息／稍後提醒」的結果
- 是否覺得提醒太早、太晚或太頻繁

本階段評估的是介入是否有用，不宣稱能準確辨認生理睡眠。

## 6. 評估指標

### 6.1 辨識與事件指標

- `reading` 被輸出為 `drowsy_like` 的誤報幀數與誤報事件數
- `sleep/drowsy` 事件命中數與漏失數
- Precision／Recall／F1（逐幀與事件層分開）
- 狀態切換次數
- onset delay：`predicted_onset - true_onset`
- `unknown_low_head` 的幀占比與持續時間
- 各類資料品質下的 coverage，不得只對可見臉幀計分後宣稱整體成效

### 6.2 快軌回歸指標

- 分心、趴下、離席事件輸出是否與凍結基準一致
- 是否新增漏失或延遲
- 慢軌是否錯誤覆蓋快軌結果

### 6.3 使用體驗指標

- 每小時不需要的詢問次數
- 每小時總詢問次數
- 使用者主觀有用率
- 相同事件是否因冷卻失效而重複轟炸

## 7. 通過條件與停止條件

### 最小通過條件

1. 同一 CSV 重跑兩次輸出逐位元相同。
2. 快軌在既有回歸影片上不得出現行為變更。
3. test10 正常閱讀／工作切換不可產生持續性的睡眠提醒。
4. test11 的刻意打瞌睡與低頭睡眠大多能形成事件；小樣本需同時回報命中個數，不只報百分比。
5. 已配對事件的延遲應符合所選 2–3 秒觀察窗，不得因 latch 錯誤延遲十幾秒。
6. 實機試用的不需要詢問暫定不超過每小時 1 次。

### 立即停止並保留失敗結果

- 正常閱讀仍長時間被判為 `drowsy_like`。
- 為修正新影片而反覆增加影片專屬門檻。
- 快軌的分心、趴下或離席結果發生回歸。
- 只有排除遮擋、轉場或 `unknown` 後數字才好看。
- 雙軌策略的改善只出現在開發影片，未通過 test10／test11。

若未通過，不繼續堆疊更多規則。下一個研究變因應改為相機擺放角度或新增感測來源，而不是繼續
調整同一組 EAR、Pitch、鼻子與肩膀門檻。

## 8. 實作與 Review 順序

每一階段完成後停下 review，不一次接入正式 App：

1. **規格**：確認狀態名稱、2／3 秒比較方式、GT 與通過條件。
2. **離線工具**：產生逐幀證據與事件檔，驗證可重現性後停下。
3. **既有資料開發**：比較 test6～test9，選定並凍結一組策略後停下。
4. **獨立影片**：拍攝與標記 test10／test11，跑完一次後無論成功失敗都先記錄。
5. **正式 App feature flag**：只有獨立驗證通過才接入，完成單元測試後停下。
6. **實機試用**：收集 45–60 分鐘自然使用紀錄，再決定是否成為預設。
